# group-manager-2 追加レビュー観点

このスキルは単体では使わない。**通常のコードレビュー(review スキル / `/code-review`)を必ず先に(または並行して)実行し、その結果にこのスキルの観点を追加する**、という使い方をする。既存レビューが拾わない「このリポジトリ固有のルール」「命名の一貫性」「保守性・可読性」の3点を機械的に取りこぼさないためのチェックリストであり、一般的なバグ検出や設計レビューの代わりにはならない。

`ReportFindings` を使う文脈(通常の `/code-review` の延長)であれば、このスキル由来の指摘も同じ形式・同じリストにまとめて追加する。category には `convention` / `naming-consistency` / `maintainability` を使う。ReportFindings を使わない文脈(会話中の簡易レビュー等)では、指摘をMarkdownの箇条書きで返す。

## 0. 前準備

差分に含まれるファイルパスから、対象ディレクトリ(`api/`, `user/`, `admin_view/nuxt-project/`, `user_front/` など)を特定する。判断に迷ったら `AGENTS.md` と `.coderabbit.yaml` の `path_instructions` を実際に読んで最新のルールを確認すること(このSKILL.mdの内容は要約であり、正はリポジトリ側のファイル)。

## 1. リポジトリのコーディング規約への準拠

`AGENTS.md`(正本)と `.coderabbit.yaml` に書かれた規約と、変更内容がズレていないか確認する。

- **api/** (Rails 6.1): 2スペースインデント、`snake_case` 命名、RESTfulなコントローラ設計。DBスキーマを変更する場合はマイグレーションが伴っているか。`api/test` 配下に正常系・バリデーション・失敗ケースのテストが追加/更新されているか。N+1やSQLインジェクションなどセキュリティ上の懸念がないか。
- **user/** (Next.js 15): コンポーネントは `PascalCase`、フック・ユーティリティは `camelCase`。スタイリングはTailwind。`.prettierrc.json` のimport順序(react → next → 外部パッケージ → 型 → `@/config` → `@/lib` → `@/components` → `@/hooks` → `@/styles` → 相対パス)や `singleQuote`/`semi`/`printWidth: 80` などのフォーマットに沿っているか。`tsconfig.json` は `strict: true` なので `any` 逃げや型の握りつぶしがないか。
- **admin_view/nuxt-project/** (Nuxt/Vue): `<template>` → `<script>` → `<style>` の順序、2スペースインデント。共通処理は各アプリの `utils/` に集約されているか。
- **全体**: ESLint/Prettier/RuboCopの警告が残っていないか。既存の実装パターン(例: APIレスポンスは `fmt(status, data)` で包む、更新系は`PATCH`を使う等)から逸脱していないか、逸脱する場合は意図的か確認する。

このリポジトリでは「is_ 等のboolean命名」や「ドキュメンテーションコメント必須」はRuboCop/ESLint側で強制されていない。つまり**Lintが通ることと、レビューで見るべき命名・可読性の質は別物**であり、下記2・3節は特にLintでは拾えない観点として重要視すること。

## 2. 変数名・メソッド名の一貫性(同じ概念には同じ名前)チェック

過去の実際のレビューで繰り返し指摘されてきたパターン。「べき等性」とは、同じ処理・同じ概念を指す名前が、ファイルや呼び出し箇所を跨いでも常に同じ形で現れる(逆に、同じ名前が別の意味で使い回されていない)ことを指す。

- **同義の実装が別名で存在していないか**: 同じ役割のメソッド/関数が既に他ファイルにあるのに、別名で新規実装されていないか(例: `openEditError` という既存関数があるのに、同じ役割の新関数を `onEditorError` のような別名で作ってしまうケース)。既存の名前に揃えるか、共通化を提案する。
- **省略しすぎていないか**: 1文字や意味不明な略語の変数名(`c` など)は、フルスペル(`category`)に直すよう指摘する。ただし過度に長い名前も可読性を落とすのでバランスを見る。
- **boolean/フラグ名が意図を一意に示しているか**: `devOpen` のように環境名(dev/prod)と紛らわしい接頭辞や、`0/1/2` のような多値をbooleanの名前(`isInternational` 等)で表現している箇所を見たら、意味の説明(コメント or 定数化)か、多値であることが伝わる命名を提案する。
- **メソッド名に条件分岐をそのまま埋め込んでいないか**: `notify_slack_if_xxx` のように `if` を含む名前は、状況によって呼ばれたり呼ばれなかったりする印象を与えて紛らわしい。「いつ何をするか」を表す動詞句(`notify_slack_on_unapproved_resubmission` 等)を提案する。
- **名前とコード上のコメント/実態が矛盾していないか**: コメントが `preload している` と書いてあるのに実装は `freeze` だけ、といった名前・コメントと実装のズレがないか確認する。
- **同じ概念が層を跨いで表記ゆれしていないか**: DB/Rails/API/フロントの間で `parent_id`⇄`parentId` のような命名規則の変換以外に、同じものを指すのに違う語(例: `descendant` と `children`)を使っていないか。フロント側で「わかりにくい」と感じる語(専門用語の直訳、システム内部用語がそのままUI文言になっている等)がないかも見る。

## 3. 保守性・可読性

過去のレビューで繰り返し出てきた具体的な指摘パターン。

- **重複コードの共通化**: 同一ロジックが2箇所以上にコピペされていないか(Railsなら `concern`、フロントなら共通コンポーネント/utilへの切り出し)。
- **責務の配置**: フロント側でAPIレスポンスを画面ごとに毎回整形・ソート・集計していないか。ドメインロジック(階層構造の整形、表示名の生成など)はAPI(Model/Controller)側に寄せるべきでないか、逆にAPI側に画面固有の表示ロジックが漏れていないか。
- **APIコール回数 / N+1**: 同一画面の初期表示で同じAPIを何度も呼んでいないか。ループの中で都度DBアクセスしていないか。
- **ネストの深さ**: 深いif文はガード節・早期return・`before_action`での前提チェックの共通化で浅くできないか。
- **マジックナンバー/マジック文字列**: 意味のある数値・文字列がそのままコードに埋め込まれていたら、意味をコメントに残した定数への切り出しを提案する。
- **デバッグ残骸**: `console.log`/`console.error`/コメントアウトされた検証コードなど、本番に不要な出力・コードが残っていないか。特に「エラーをconsoleに出すだけでユーザーへの通知がない」パターンは、UXの問題として指摘する。
- **未使用コード**: どこからも参照されていない関数・変数・importが残っていないか(過去のライブラリ移行の残骸などを含む)。
- **コメントの質**: コードを読めば分かる「何をしているか」の説明コメントは削除を提案する。逆に「なぜこの実装/この値なのか」「既知の制約・TODO」など読んだだけでは分からない理由は、コメントとして残す/追加するよう促す。
- **値表現の統一**: 「未指定」を表す値がDB(`NULL`)・Rails(`nil`)・API(`null`)・フロント(`""`)の間でズレていないか。空文字とnil/nullの意味を混同していないか(バリデーションはモデル層に寄せる)。
- **権限・認可漏れ**: 似た既存画面で `$role` 等によるロール別の操作制限がある場合、新規実装・移植したコードでも同じ制限が実装されているか(実装漏れはセキュリティ上の懸念として最優先で指摘する)。
- **エラーハンドリングの漏れ**: `try/catch` の対応関係、`finally` でのリソース解放漏れ(タイマーの `clearTimeout` など)、失敗時のユーザー通知漏れがないか。
- **Fixture/Seedの依存順序**: `db/fixtures` を変更した場合、参照先(親)より先に投入される順序になっていないか。

## 出力

`ReportFindings` を使う場合は通常のレビュー結果と1つのリストにまとめ、このスキル由来の指摘には `category: convention` / `naming-consistency` / `maintainability` のいずれかを付ける。それ以外の場合は、通常レビューの結果に続けて「### 追加観点(規約・命名・保守性)」として箇条書きで示す。指摘が無ければ「該当なし」と明記し、無理に指摘を作らない。

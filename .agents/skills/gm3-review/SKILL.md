# GM3 コードレビュー

コードの変更、commit、push、branch の切り替え、worktree の作成、GitHub への投稿は行わない。

## 対象

- 指定された PR、branch、commit、diff range を優先する。
- 指定がなければ `origin/gm3/develop...HEAD` を見る。
- PR の場合は、本文、関連 Issue、既出コメント、base、head も読み取り専用の `gh` コマンドで確認する。
- 再レビューでは、前回以降の修正と前回の指摘だけを確認する。追加指摘は修正が持ち込んだ問題に限る。

## 最初に確かめること

適用される `AGENTS.md`、PR 本文、関連 Issue、差分の周辺コード、呼び出し元、テスト、base 側の実装を読む。レビューの冒頭に、この PR の目的を一文で書く。

- PR と Issue が宣言している範囲を確認する。範囲外の欠落は必須修正にせず、確認事項か別 Issue 候補に分ける。
- `user`、`admin_view`、`rental`、`user_front` のどれが、どの API を、どの権限で呼ぶかを追う。仕様どおりの 403 を不具合として扱わない。
- 設計の方向への反対と、合意された設計に対する実装漏れを分ける。設計への反対は blocker と断定せず、作者への確認事項にする。

## 指摘候補を判定する五つの問い

候補を見つけたら、次を順に確かめる。

### 1. この PR が持ち込んだ問題か

base 側のコード、`git log`、`git blame` で確認する。この PR の回帰は指摘し、以前からある問題は別 Issue 候補へ分ける。base でも失敗する CI は blocker にしない。ただし、新しい endpoint の認証漏れなど、この PR が新しく作ったリスクはこの PR で閉じる。

### 2. 実際の操作で到達するか

フロントの呼び出しと運用手順から、問題の入力や状態へ到達する経路を示す。たとえば実際には新規追加ではなく PUT による編集になるなら、新規追加を前提にした重複の指摘は採用しない。現在の呼び出し元から到達しない防御的な指摘は除外する。

### 3. 実データで起きるか

利用可能なデータ、件数、業務上の前提を確認する。対象データが存在しない、重複がない、業務上 1 対 1 が保証されるなどの根拠があれば重大度を下げるか取り下げる。実データを確認できなければ、推測で blocker にせず未確認の前提として書く。

### 4. この規模と運用に見合うか

学園祭運営の利用者数、同時操作数、失敗時の影響に照らして判断する。具体的な頻度と損害を示せないまれな競合への DB 制約、大規模な回帰テスト、メール送信への Outbox パターンなどを必須にしない。一方、認可、秘密情報、不可逆なデータ損失、通常操作やデプロイの失敗は規模にかかわらず重く扱う。

### 5. リポジトリの既存のやり方と合うか

同種の endpoint、周辺コード、既存テスト、設定を調べる。一般論の best practice より、リポジトリ内の一貫性と既存パターンに沿う最小修正を優先する。他の箇所でも同じ運用をしている設定は、この PR だけの欠陥にしない。

## 重点的に見る観点

五つの問いを通過した候補について、次を確認する。

- 正常系だけでなく、`nil`、空、複数件、途中失敗、transaction の扱い
- 認証、認可、他団体のデータへ到達できないこと
- API と各フロントの request / response の整合
- 既存機能の回帰
- migration の可逆性と既存データとの互換性
- UI の loading、empty、error、二重操作などの状態
- テストが実際の挙動を検証していること

認可漏れ、秘密情報の露出、不可逆なデータ損失、通常操作や本番デプロイの失敗、API とフロントの不整合は merge を止める。AI や bot が付けた重大度はそのまま採用しない。

PR 本文の検証結果や bot の「修正済み」は、コード、履歴、テスト、可能なら再現で確かめる。確認は対象に必要な最小範囲にする。

## 実行

subagent が利用できる場合は、一つのレビュー用 subagent に対象と上記基準を渡し、結果を待つ。複数へ分割して重複した指摘を出さない。利用できない場合は直接レビューする。

## 出力

日本語で、最初に `PR の目的` を一文で書き、その後に指摘を重大度順で書く。各指摘には次を含める。

- `file:line`
- どの入力・操作で何が壊れるか
- この PR が原因である根拠
- 既存パターンに沿う最小の修正案

続けて、問題がなかった主な観点と、実行できなかったテストや確認できなかった前提を書く。再レビューでは各指摘を `RESOLVED`、`PARTIALLY`、`NOT RESOLVED` で判定する。

最後の一行は、merge を止める指摘があれば `REQUEST_CHANGES`、なければ `APPROVE` とする。問題がなければ無理に指摘を作らない。

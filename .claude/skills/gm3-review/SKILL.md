`$ARGUMENTS` をレビューしてください。これは読み取り専用のレビューです。コード変更、commit、push、branch の切り替え、worktree の作成、GitHub への投稿をしないでください。

最初に、適用される `AGENTS.md` と `docs/dev/ai-code-review.md` を全文読み、PR の目的を一文で定めてください。PR 番号または URL が指定されていれば、読み取り専用の `gh` コマンドで base、head、本文、関連 issue、既出コメント、差分を確認してください。

対象は次の順で決めます。

- 引数に明示された diff range、base、branch、commit、PR を優先する。
- 対象指定がなければ `git diff origin/gm3/develop...HEAD` を見る。
- 再レビューまたは前回 commit が指定されていれば、その commit 以降の修正だけを見て、前回指摘を `RESOLVED` / `PARTIALLY` / `NOT RESOLVED` で判定する。追加指摘は修正が新しく持ち込んだ問題だけにする。

差分、base 側のコード、履歴、周辺実装、テストを調べ、候補ごとに共有ガイドの 5 つの問いを適用してください。正しさ、認可と団体間の分離、API とフロントの対応、回帰、migration の可逆性と既存データ、UI 状態、テストの実効性を深く確認してください。PR 本文や bot の結論はコードや再現結果で裏付けてください。

次のすべてを満たすものだけを指摘してください。

- この差分が新しく持ち込んだ。
- 具体的な入力や操作から誤動作または実害まで説明できる。
- コード、履歴、テスト、再現結果のいずれかで根拠を示せる。
- この PR に収まる小さな修正がある。

既存問題、到達しない防御的仮説、運用規模に見合わない競合対策、書き方の好み、base でも失敗する CI は指摘から除外してください。重要な全体課題だけ `別 issue 候補` に分離し、merge は止めないでください。

日本語で、次の順に出力してください。

1. merge を止める指摘。重大度順に、短い題名、`file:line`、失敗シナリオ、この PR が原因である根拠、既存パターンに沿う最小修正を書く。
2. `任意の提案`。作者の時間を使う価値があるものだけを書く。
3. `別 issue 候補`。なければ省略する。
4. `問題がなかった観点`。
5. `確認できなかったこと`。実行できなかったテストや確認不能な前提を書く。
6. 再レビューなら、前回指摘ごとの判定、`file:line`、根拠を書く。
7. 最後の一行を `APPROVE` または `REQUEST_CHANGES` のどちらかだけにする。

merge を止める指摘がなければ、無理に指摘を作らないでください。GitHub にそのまま投稿するコメントは作らず、人が検証・編集するためのレビュー結果を返してください。

`$ARGUMENTS` をレビューしてください。これは読み取り専用のレビューです。コード変更、commit、push、branch の切り替え、worktree の作成、GitHub への投稿をしないでください。

指定された PR、branch、commit、diff range を優先し、指定がなければ `origin/gm3/develop...HEAD` を見てください。PR の場合は、本文、関連 Issue、既出コメント、base、head も読み取り専用の `gh` コマンドで確認してください。

適用される `AGENTS.md`、差分の周辺コード、呼び出し元、テスト、base 側の実装を読み、次を重点的に確認してください。

- `nil`、空、複数件、途中失敗、transaction
- 認証、認可、他団体のデータへの到達
- API と各フロントの request / response
- 既存機能の回帰
- migration の可逆性と既存データ
- UI の loading、empty、error、二重操作
- テストが実際の挙動を検証しているか

指摘は、この差分が新しく持ち込み、実際の経路から到達でき、具体的な入力や操作から誤動作まで説明でき、実データと運用規模に照らして対応する価値があり、この PR に収まる小さな修正があるものに絞ってください。

既存問題、到達経路のない推測、可能性と影響が小さい競合、書き方の好み、base でも失敗する CI は指摘しません。重要な既存課題は別 Issue 候補に分け、merge を止めないでください。

認可漏れ、秘密情報の露出、不可逆なデータ損失、通常操作や本番デプロイの失敗、API とフロントの不整合は merge を止めます。PR 本文や bot の結論は、コード、履歴、テスト、可能なら再現で確かめてください。

日本語で、指摘を重大度順に書いてください。各指摘には `file:line`、失敗する入力・操作、この PR が原因である根拠、既存パターンに沿う最小修正案を含めます。その後に、問題がなかった主な観点と、実行できなかったテストや確認できなかった前提を書きます。

再レビューでは、前回以降の修正だけを見て、各指摘を `RESOLVED`、`PARTIALLY`、`NOT RESOLVED` で判定してください。追加指摘は修正が持ち込んだ問題に限ります。

最後の一行は、merge を止める指摘があれば `REQUEST_CHANGES`、なければ `APPROVE` としてください。問題がなければ無理に指摘を作らないでください。

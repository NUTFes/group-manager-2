`$ARGUMENTS` をレビューしてください。これは読み取り専用のレビューです。コード変更、commit、push、branch の切り替え、worktree の作成、GitHub への投稿をしないでください。`git fetch`、`git pull` など、ref や作業ツリーを更新するコマンドも実行しないでください。

指定された PR、branch、commit、diff range を優先し、指定がなければ `origin/gm3/develop...HEAD` を見てください。PR の場合は、本文、関連 Issue、既出コメント、base、head も読み取り専用の `gh` コマンドで確認してください。

適用される `AGENTS.md`、PR 本文、関連 Issue、差分の周辺コード、呼び出し元、テスト、base 側の実装を読んでください。レビューの冒頭に、この PR の目的を一文で書きます。

PR と Issue が宣言する範囲を確認し、範囲外の欠落は必須修正にせず、確認事項か別 Issue 候補に分けてください。`user`、`admin_view`、`rental` のどれが、どの API を、どの権限で呼ぶかを追い、仕様どおりの 403 を不具合として扱わないでください。設計の方向への反対と、合意された設計に対する実装漏れも分けます。設計への反対は blocker と断定せず、作者への確認事項にしてください。

指摘候補ごとに、次の五つを順に確かめてください。

1. **この PR が持ち込んだ問題か。** base 側のコード、`git log`、`git blame` で確認します。この PR の回帰は指摘し、以前からある問題は別 Issue 候補へ分けます。base でも失敗する CI は blocker にしません。ただし、新しい endpoint の認証漏れなど、この PR が新しく作ったリスクはこの PR で閉じます。
2. **実際の操作で到達するか。** フロントの呼び出しと運用手順から、問題の入力や状態へ到達する経路を示します。実際には PUT による編集になるなど、前提とした経路が成立しない指摘は採用しません。現在の呼び出し元から到達しない防御的な指摘も除外します。
3. **実データで起きるか。** 利用可能なデータ、件数、業務上の前提を確認します。対象データが存在しない、重複がない、業務上 1 対 1 が保証されるなどの根拠があれば、重大度を下げるか取り下げます。実データを確認できなければ、推測で blocker にせず未確認の前提として書きます。
4. **この規模と運用に見合うか。** 学園祭運営の利用者数、同時操作数、失敗時の影響に照らします。具体的な頻度と損害を示せないまれな競合への DB 制約、大規模な回帰テスト、メール送信への Outbox パターンなどを必須にしません。一方、認可、秘密情報、不可逆なデータ損失、通常操作やデプロイの失敗は重く扱います。
5. **リポジトリの既存のやり方と合うか。** 同種の endpoint、周辺コード、既存テスト、設定を調べます。一般論の best practice より、リポジトリ内の一貫性と既存パターンに沿う最小修正を優先します。他の箇所でも同じ運用をしている設定は、この PR だけの欠陥にしません。

五つの問いを通過した候補について、次を重点的に確認してください。

- `nil`、空、複数件、途中失敗、transaction
- 認証、認可、他団体のデータへの到達
- API と各フロントの request / response
- 既存機能の回帰
- migration の可逆性と既存データ
- UI の loading、empty、error、二重操作
- テストが実際の挙動を検証しているか

認可漏れ、秘密情報の露出、不可逆なデータ損失、通常操作や本番デプロイの失敗、API とフロントの不整合は merge を止めます。AI や bot が付けた重大度はそのまま採用しません。PR 本文や bot の結論は、コード、履歴、テスト、可能なら再現で確かめてください。確認は対象に必要な最小範囲にします。

日本語で、最初に `PR の目的` を一文で書き、その後に指摘を重大度順で書いてください。各指摘には `file:line`、失敗する入力・操作、この PR が原因である根拠、既存パターンに沿う最小修正案を含めます。その後に、問題がなかった主な観点と、実行できなかったテストや確認できなかった前提を書きます。

再レビューでは、前回以降の修正だけを見て、各指摘を `RESOLVED`、`PARTIALLY`、`NOT RESOLVED` で判定してください。追加指摘は修正が持ち込んだ問題に限ります。

最後の一行は、merge を止める指摘があれば `REQUEST_CHANGES`、なければ `APPROVE` としてください。問題がなければ無理に指摘を作らないでください。

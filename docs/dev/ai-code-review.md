# AI と行うコードレビューの観点

この文書は、nutmeg が group-manager-2 の PR を Codex、Claude、CodeRabbit、Copilot などでレビューするときの判断基準です。AI の出力は指摘候補として扱い、人が事実を確かめて採否と重さを決めます。

AI の指摘をすべて直すと、差分が膨らみ、merge が遅れ、作者の負担が増えます。一方、読まずに approve すると、本当に危険な問題を見落とします。この文書は、その間で判断するために使います。

## 全体の流れ

1. AI に指摘候補を出させる。
2. 人が候補ごとに根拠を問い直す。
3. 「この PR で直す」「任意の提案」「別 issue」「取り下げる」に振り分ける。
4. この PR で直すものだけを、理由と最小の直し方を添えてコメントする。

`blocker` は merge を止める指摘です。AI が付けた `BLOCKER` や「必須」は採用せず、この文書の基準で付け直します。

## 指摘を読む前に確認すること

- PR の目的を一文で言えるようにする。
- PR 本文と issue のテスト項目から、宣言された範囲を確認する。
- 差分だけでなく、どのフロントが、どの API を、どの権限で呼ぶかを見る。
- 設計そのものへの反対と、合意済みの設計に対する実装漏れを分ける。設計への反対は、個別コメントより先に作者と話す。
- 範囲外の欠落は修正要求にせず、「この PR に含めるか」という確認か別 issue にする。

group-manager-2 には `user`、`admin_view`、`rental`、`user_front` など、目的と権限が異なるクライアントがあります。設定どおりに 403 を返す API を、差分だけ見て故障と判断しないでください。

## 指摘ごとに確かめる 5 つの問い

### 1. この PR が持ち込んだ問題か

base ブランチ、`git show`、`git blame`、履歴を使い、問題が PR より前から存在したかを確認します。

- この PR が持ち込んだ回帰は、この PR で直す。
- もともとあった問題は、原則として別 issue にする。
- base でも落ちる Rails test、RuboCop、lint などは、この PR の blocker にしない。
- 新しく追加した API の認証など、PR が新しく作るリスクはこの PR で閉じる。

全体に共通する認証不足を一つの PR だけで直すと、API ごとの基準が不統一になります。その場合は、全 API を調査する issue として一括で扱います。

### 2. 実際の操作で到達するか

理論上の入力だけでなく、現在のフロント、API クライアント、運用手順からその入力が来るかを確認します。

たとえば、再登録で重複行が生じるように見えても、実際の画面が新規追加ではなく PUT による編集を使うなら、想定した経路は成立しません。現在の呼び出し元から到達しない防御的な指摘は、原則として投稿しません。

### 3. 実データで起きるか

migration、ID 変更、重複統合などの指摘は、本番相当の件数と値を確認します。

- 対象テーブルが空なら、既存データ消失のシナリオは成立しないことがある。
- 全件集計で重複がなければ、複雑な統合処理は不要なことがある。
- 学籍番号と氏名の対応など、業務上の不変条件を確認する。

「本番データがない」という根拠を採用した場合は、approve の前提に残します。

### 4. 規模と運用に見合うか

group-manager-2 は学園祭運営のシステムで、利用者数と同時操作数は限られます。決済や銀行システムと同じ堅牢性を一律に要求しません。

次のような提案は、具体的な頻度と損害が示されない限り過剰になりやすいものです。

- まれな同時操作だけで生じる重複を防ぐための大規模な DB 制約追加
- 小さなメール送信処理への Outbox パターン導入
- 変更の危険度に比べて大きすぎる回帰テスト群

ただし、認可、秘密情報、不可逆なデータ損失、通常操作やデプロイの失敗は利用規模にかかわらず重く扱います。

### 5. リポジトリの既存のやり方と合うか

一般論の best practice より、まず周辺コード、同種 endpoint、既存テスト、設定ファイルを調べます。新しい仕組みを持ち込む前に、既存パターンで直せるかを探します。

他の箇所でも同じ運用をしている stage 環境変数などは、新しい PR だけの欠陥として扱いません。一貫性そのものに問題がある場合は、全体課題として別 issue にします。

## merge を止める基準

次は原則として blocker です。

- 認可の抜けにより、他団体のデータを閲覧・操作できる。
- 秘密値がログ、履歴、URL などに露出する。
- migration、削除、統合処理で、戻せないデータ損失が生じる。
- 通常操作または本番デプロイで壊れる。
- API を変更したが、実際のフロント呼び出しが追従していない。

次は原則として、この PR の blocker にしません。

- 差分外の既存問題。
- 全体設計の課題。
- 頻度も損害も小さい同時操作の競合。
- テスト環境だけの設定差。
- 機能に関係しない lint や base でも落ちる CI。
- 直すと無関係な大差分が混ざるもの。OpenAPI 全再生成などは、必要性と差分を分けて判断する。

## 修正案を小さくする

- API 全体、全呼び出し元、OS バージョンまで変える案が出たら、PR 内で済む最小修正を探す。
- 関数の呼び順変更など、既存設計を保つ修正を優先する。
- 新しい仕組みを足す前に、リポジトリの既存パターンへ合わせる。
- PR の目的と無関係な一括変更は戻す。`find` から `find_by` への変更など、例外と `nil` の挙動差にも注意する。
- 大事でも範囲外の設計課題は、PR コメントではなく issue やメモに残す。

## AI の出力を検証する

- 「どの入力で起きるか」「どの経路で到達するか」「他の箇所はどうか」を問い直す。
- 自分が説明できない指摘は投稿しない。
- 静的な指摘は、可能なら Docker、テスト、ブラウザで再現する。
- 複数 AI の結論が食い違ったら、コードと実行結果で人が判断する。
- bot の「修正済み」は、コードとテストの両方で確認する。
- review は原則として PR の branch を checkout した状態で行う。checkout していない場合は、実行できなかった確認を明記する。

## コメントの書き方

- 結論を先にし、何を直せば approve できるかを書く。
- 何が、なぜ問題で、どう直すかを一つのコメントに一つずつ書く。
- 一か所なら GitHub suggestion、複数ファイルなら小さな diff を示す。
- 学生メンバーに伝わる相談の口調を使い、AI の造語や過剰な重大度ラベルを避ける。
- 意図が不明なら質問し、再現できた事実は断定する。
- 別 issue に回した内容は PR に書かない。
- 他人の PR へ reviewer が直接 commit しない。

## 再レビューと approve

- 再レビューは前回指摘の解消確認に絞る。
- 新しい指摘は、修正が新しく持ち込んだ問題だけにする。
- approve 文面には、確認した修正、実行したテスト、採用した前提、デプロイ時の確認事項を書く。
- 根拠付きで見送った指摘は、根拠を確認して前提として残す。
- approve と merge は別の判断とする。他 PR への依存があっても、順番が明記されていれば approve できる。
- merge 前に環境変数、本番 migration、main で動く CI も確認する。

## agent に依頼するときの入力

依頼には次を含めます。

- 対象 diff、base branch、PR の目的。
- 読むべき `AGENTS.md`、issue、既存コード、テスト。
- 実装前提と設計選択も疑い、PR 本文の検証結果を鵜呑みにしないこと。
- 正しさ、認可、API とフロント、回帰、migration、UI 状態、テストの実効性という観点。
- 既存問題、具体的な入力を説明できない推測、書き方の好みを除外すること。
- CodeRabbit などで既出・対応済みの指摘。
- 各指摘の `file:line`、失敗シナリオ、根拠、最小修正案。
- 問題がなかった観点と、実行できなかった確認。
- 最後に `APPROVE` または `REQUEST_CHANGES` を一行で出すこと。
- コード変更と GitHub 投稿をしないこと。

### 初回レビューの依頼例

```text
PR #<番号> を review してください。対象は git diff origin/gm3/develop...HEAD です。
PR の目的: <目的を 1〜2 文>
AGENTS.md、関連 issue、既存コード、テストを読んでください。

実装の前提と設計の選択も疑い、PR 本文の検証結果をコードで確かめてください。
正しさ、認可、API とフロントの対応、回帰、migration、UI 状態、テストの実効性を確認してください。

この PR が新しく持ち込んだ問題だけを指摘してください。既存問題、具体的な入力から誤動作まで説明できない推測、書き方の好みは除外してください。
対応済みの指摘: <一覧>

重大度順に file:line、失敗シナリオ、根拠、最小修正案を書いてください。問題がなかった観点と、確認できなかったことも書いてください。
最後に APPROVE または REQUEST_CHANGES を一行で書いてください。
コード変更と GitHub 投稿はしないでください。
```

### 再レビューの依頼例

```text
前回レビュー後の修正（git diff <前回 commit>...HEAD）だけを見てください。
前回の各指摘を RESOLVED / PARTIALLY / NOT RESOLVED で判定し、file:line と根拠を書いてください。
修正が新しい問題を持ち込んだ場合だけ追加で指摘してください。
コード変更と GitHub 投稿はしないでください。
```

## 人が投稿前に確認するチェックリスト

- PR の目的と範囲を説明できる。
- 各指摘がこの PR 由来かを確認した。
- 実操作と実データで起きるかを確認した。
- merge を止める重さをこの文書で付け直した。
- 既存問題と範囲外課題を PR から外した。
- 自分が説明できない指摘を投稿していない。
- コメントに何を、なぜ、どう直すかを書いた。
- approve の前提と確認内容を残した。
